# v3.2.6 改动与验收

## 对本轮问题的结论

1. **同步时简介按钮转动**：旧界面复用了全局 loading；这不是 AI 在偷偷重写备注。后台同步确实会重建基础索引，但手动备注由 overrides 保留。现在简介按钮单独表示“重新读取简介”，明确是本地提取；修复主动清空备注后又显示自动内容的问题。
2. **4K 模糊与首页**：星图曾限制 DPR 为 1.35，画布总像素约 170 万；在 4K 上放大后必然模糊。改为按实际 DPR 渲染，保留 16,777,216 像素资源上限，响应跨屏缩放。新增独立 SVG 群岛视图，以来源或文件夹为单位，数字为准确数量，岛屿大小为分档提示；原星图保留。
3. **INSPECTOR / V0**：删去无实际任务价值的占位区域及说明，技能库改为筛选栏与内容双列，窄窗单列。
4. **PaperSpine**：本机两份来自同一 GitHub 仓库。问题是预览按 URL 识别、正式写入仍按目录名判断。现在在正式写入前重新核验仓库身份；大小写、`.git` 和 SSH 写法归一；实际 Git origin 与导入记录不一致时停止自动处理。标题优先显示项目名，作者次级显示；用户自定义标题不被覆盖。
5. **参考项目借鉴**：本机发现、管理状态、路径分组、搜索分页、原文预览、来源身份与调用入口已经落地；并非所有参考仓库功能都完整移植。详见审计报告中的真实能力矩阵与差距清单。本轮为独立实现，没有批量复制第三方源码或技能内容。
6. **Prompt 调用**：资料页可输入任务并复制组合文本；可以创建独立 SKILL.md 调用入口，由受支持的本地 Agent 读取原 Prompt 目录。原资料不改类型、不覆盖；不会自动执行其中脚本。创建入口时尝试投递，投递失败保留入口并显示提醒。
7. **排版**：来源数、Prompt 数统一网格与数字对齐；项目名/作者分层；删除 INDEX/FILTER、V0 等无用标签，精简报告生成与同名技能说明。
8. **新装 AI 工具**：新增“连接 Skills”，使用现有安全投递机制重建链接并刷新检测，不需要先联网更新仓库。实际中央投递仍是 Claude Code、Codex、Antigravity；MCP 配置管理仍限已实现适配器。其他工具的扫描规则不等于自动配置支持。
9. **本机 Skills 长列表**：同一真实目录合并成一项，保留多客户端路径入口；每页 20 项，滚动限制在列表区域，过滤后重置页码。
10. **“复制到技能库”**：表示外部原件尚未归本软件管理；不是因功能相似被隔离。复制后有独立受管副本，外部原件保留。暂不做双向自动同步，避免两边修改互相覆盖。
11. **同名子 Skill**：各父来源下全部保留，可在同一任务指定多个父 Skill。底层来源边界用于精确寻址，不是能力淘汰。修复父路由引用其他来源、junction 越界的缺陷。是否实际并行执行，仍由调用的 Agent 决定。
12. **发布范围**：本轮目标为 3.2.6 本机覆盖升级和源码推送；公开 Release/自动更新渠道需单独验证产物，不能由本机版本号推断已经发布。

## 重复来源的可恢复合并

先核验实时仓库身份、逐文件内容及空目录，再备份 SQLite、配置和重复目录。主来源的设置优先，合并备注/标签，保留另一分类的记录。存在不同内容、链接、或重复来源的子 Skill 个性化元数据时停止自动合并，不猜测覆盖关系。配置中的重复仓库也同步归一，避免下次同步重新生成副本。

多进程写操作共享文件排他锁。正常失败尝试恢复目录、配置和投递；完整备份仍保留。这不是跨 SQLite/文件系统的断电原子事务，自动断电恢复日志仍是后续工程。

## 尚非最优解的部分与下一步

| 优先级 | 缺口 | 可验收的下一步 |
|---|---|---|
| P1 | 更多客户端只检测、不支持中央投递 | 每次补一个官方适配器，分别验证未安装不写入、安装后连接、卸载后清理、外部已有数据保留；不批量猜路径 |
| P1 | 外部副本缺少双向更新 | 先增加内容差异预览与单向手动更新，再做带版本基线的双向合并；冲突不覆盖 |
| P1 | 跨目录和数据库写操作不是断电原子事务 | 持久操作日志、启动重放、故障注入覆盖每个阶段 |
| P2 | 项目级工作区扫描不持久 | 保存显式添加的项目根，显示扫描范围和离线状态 |
| P2 | 自动摘要可能误取 README 导航 | 提升段落筛选，保留手写内容所有权；用导航/多语言/目录型 README 夹具验收 |
| P2 | App.tsx/lib.rs 过大，维护成本高 | 按业务边界逐步拆分；每次只迁移一个已有模块，保持接口与回归通过 |

不宣称全项目零缺陷、所有客户端通用或已完成朋友 Windows 10 阴影验收。

## 本机 PaperSpine 补充核验

两份来源 HEAD 同为 f7e3dab，但新增副本启用了 sparse-checkout。逐项对比得到 586 个仅完整副本存在的文件/目录；新增副本没有独有或不同内容的条目。因此合并规则支持严格包含：重复副本的每个文件哈希和目录都必须在保留副本中一致存在。不会丢弃新内容或用户修改，目录和数据库仍先备份。
