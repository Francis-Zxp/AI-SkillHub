# v3.2.18 — Client discovery correction

Status: local validation candidate; public release remains 3.2.17.

## Confirmed causes

1. WorkBuddy discovery searched three default paths ending in `WorkBuddy.exe`. The installed WorkBuddy AI 5.6.2 registers `WorkBuddyAI.exe` in a custom D: location, with an empty InstallLocation and a populated DisplayIcon.
2. Delivery used `.codebuddy/skills`. The installed application's public product metadata sets `dataFolderName` to `.workbuddy-ai`; its runtime reads `<configDir>/skills`. `.workbuddy` is a fallback, and `.codebuddy` belongs to the separate CodeBuddy product.
3. The UI catalog listed 13 tools, but diagnostics collected only four. Installation, Skill directory discovery, and supported automatic delivery were conflated. The cached Antigravity row could also be cleared simply because its CLI was absent.
4. Codex plugin doctor's default invocation did not supply registered desktop package roots. Its generic recursive cache traversal descended into runtime dependencies and stopped early at a shallow depth.
5. Coze 1.1.43 scans only ordinary direct child directories (`Dirent.isDirectory()`), skipping junctions. The screenshot's 1 / 1 / 0 Skills exactly matches the real ordinary-folder counts in `.codex/skills`, `.agents/skills`, and `.claude/skills`. A successful directory link is not sufficient for this client.

## Changes

- Discover Windows clients from registered installation evidence, default executable paths, and bounded process evidence. Never execute a registry command string; stale records without a matching executable are ignored.
- Resolve WorkBuddy's installed profile from bounded product metadata (2 MiB; real 5.6.2 metadata is 386,464 bytes), with validated single-component folder names. Respect absolute WORKBUDDY_CONFIG_DIR / CODEBUDDY_CONFIG_DIR overrides.
- Use the same installation priority and profile rules in Rust and the shared PowerShell helper. Preserve existing WorkBuddy and CodeBuddy files; only reconcile AI SkillHub-owned links.
- Add probes for all 13 listed tools. Label discovery-only adapters explicitly. Correct desktop-only diagnostics without requiring an unnecessary CLI.
- Add Coze as the 14th adapter. Detect its registered desktop executable, offer a dedicated compatibility directory for manual addition, and report that authorization in Coze is still required. Do not create a speculative `.coze/skills` path or change Coze permissions/cloud Skills.
- Personal Skills and unrelated directory links no longer count as SkillHub-managed delivery. Require readable SkillHub-owned directory links; keep ordinary inventory separate.
- Provide `UserData/skills-catalog` as an ordinary-directory compatibility scan root. Its lightweight manifests preserve original names/descriptions and point to the authoritative Skill definitions and resource directories. Use the same enabled allowlist as client delivery; update and remove intact generated entries on synchronization. Refuse overwriting modified or unknown manifests. Existing client directory links stay unchanged.
- Codex plugin doctor reads current-user official MSIX registration and validates the manifest identity/version. Scan manifests breadth-first, skip dependencies/templates, retain entry and depth limits, and keep zero-write behavior.

## Reference verification

[skills-manager adapter catalog](https://github.com/xingkongliang/skills-manager/blob/main/src-tauri/src/core/tool_adapters.rs) separates WorkBuddy and CodeBuddy and supports extra scan roots. Its current WorkBuddy path is `.workbuddy/skills`; copying that path alone would still fail for this installed WorkBuddy AI version. The reference uses directory existence as installation detection, which can accept residue; this implementation keeps executable evidence separate. Reference license: MIT. No source code was copied.

Installed WorkBuddy AI 5.6.2 was inspected read-only: product.json dataFolderName, `resolveWorkbuddyConfigDir`, `getWorkbuddySkillsDir`, directory-link following, and `SkillsVersionEmitter` (1-second debounce). Reopen its Skills list after syncing. Detection and delivered manifests do not establish a successful model invocation.

The reference project has no Coze adapter in the inspected catalog. [Coze's official local Skills instructions](https://docs.coze.cn/cozespace_using_skills) require local file access, adding a scan directory, and adding the desired Skills to a cloud Agent conversation. This computer has Coze 1.1.43 in a custom D: installation. A desktop installation alone does not verify those grants or cloud selections.

Coze's installed `resources/app.asar → main/main.js` was inspected as text: default roots at line 101369; string metadata checks at 101454; `scanner_scanDir` at 101488; root existence filtering at 101503. No installed third-party code was executed or changed. Shared `.agents/skills` is a useful convention, not a guarantee that every tool follows links or uses the same discovery rules.

## Acceptance boundary

The compatibility catalog follows the existing parent-entry delivery allowlist. It is not a filesystem access boundary. An existing parent router may still reference a disabled child while other children in that source remain enabled; this predates the compatibility catalog and is not changed by this detection repair. Do not claim that catalog generation prevents all access to disabled child files.

Coze's directory authorization, personal-device Skill selection, and actual model invocation still require host-side acceptance. The installed scanner was inspected and its ordinary-folder discovery rule was reproduced in the compiled test; this is not a claim that a Coze conversation has already executed those Skills.

The user's friend reports successful installation after changing the Windows security setting. This is recipient installation feedback, not evidence of acceptance with Smart App Control enabled. No Windows security settings were changed by this repair.
