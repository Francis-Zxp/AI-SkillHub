# v3.2.16 DPI and client-delivery validation

## Scope and delivery boundary

Initially validated as a local-only bugfix. On 2026-10-05 the user explicitly authorized GitHub publication after another Claude Desktop audit. The user requested a fix for mixed-DPI sidebar placement, Claude Desktop local Code discovery, an unwanted navigation scrollbar, and WorkBuddy support.

## Findings and changes

- A general 980 px responsive rule made the navigation footer horizontal, while later Atlas rules kept the sidebar vertical. Explicit column/nowrap rules now keep desktop navigation consistent; the footer cannot shrink into the navigation. The minimum native width is 860 logical pixels.
- An intermediate navigation overflow change introduced the small horizontal scrollbar shown in the user's screenshot. It was reverted before packaging; navigation uses visible overflow for its tooltips.
- Moving between monitors can change devicePixelRatio without changing CSS bounds. The island renderer now listens to resolution changes, rearms the listener, resizes and removes it on disposal.
- Claude discovery missed Desktop's embedded local Code runtime under the user's roaming Claude directory. Bounded version/build probing now participates in Rust discovery, PowerShell diagnostics and delivery. A separate global CLI is unnecessary. An empty Desktop directory alone does not authorize creating a Skills directory.
- WorkBuddy code-development Skills use the product-documented `~/.codebuddy/skills` directory. Detection, diagnostics, delivery and global/project scanning are included; `.workbuddy/skills` is read-only compatibility scanning. General-task package import and MCP automatic configuration are not claimed as supported by this delivery path. WorkBuddy is not installed on this test computer.

## 2026-10-05 Windows Smart App Control block on recipient

The recipient supplied a Windows Smart App Control dialog blocking the downloaded 3.2.16 installer because the publisher could not be verified. `Get-AuthenticodeSignature` on the public installer and installed executable returned `NotSigned`; the Tauri `.sig` checked previously only authenticates updater bytes and does not establish Windows publisher trust. The same official Tauri Windows updater exits the running app after launching the installer, so a subsequent policy block appears as an abrupt exit. This is an evidence-backed explanation, not a confirmed event-log diagnosis from the recipient machine.

The public distribution gate now requires valid Windows Authenticode signatures on both the application executable and NSIS installer, with an RSA publisher certificate. A separate `-AllowUnsignedLocalCandidate` switch is limited to local testing and cannot write the public fallback manifest. The current 3.2.16 candidate was correctly rejected by the new gate. No trusted code-signing certificate is available on this machine. The GitHub release and updater were rolled back to 3.2.15 pending a certificate-backed rebuild; installed 3.2.16 clients remain installed and are not downgraded. The prior publication verification above confirms byte integrity, not compatibility with Smart App Control.
