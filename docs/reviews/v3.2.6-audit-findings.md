### 重复创建的代码机制

原 `build_github_source_import_plan` 能用 owner/repo 找到 `duplicate`，并显示“刷新已有来源，不会重复创建”，但 `target_path` 仍无条件取 `github_source_storage_name(owner, repo)`。旧目录叫 `PaperSpine`，新目标叫 `WUBING2023--PaperSpine`，故字符串路径不相等。

实际 `promote_staged_source_import_in_connection` 又从 staged 来源生成 owner--repo，后续仅判断这个目标路径是否存在，没有复核已有来源的仓库身份。于是预览和执行都没有真正复用已有目录。原始实现位于本轮修改前约 11738、11382 行；当前对应函数约 12028、11659 行。

正确约束是：规范化 GitHub owner/repo 作为身份；不同 owner 必须视为不同仓库；在受管目录中核实已有 Git origin/托管标记，复用已验证路径；执行时再次核查，不能只依靠预览时数据库状态。

`source_identity::canonical_github_identity` 接受常规 HTTPS/HTTP、git@ SSH、ssh://git@、owner/repo，规范化大小写及 `.git`，拒绝凭据、伪 GitHub 域名、编码路径分隔符、query、fragment 和子路径。不用 repo 名单独判断同仓库。

## 3. 父子路由：隔离现状与补丁

当前设计已经是按来源保留父入口，而非在全局选一个同名子 Skill 胜者：

- `lib.rs:2167` `select_agent_skill_allowlist_entries` 排除旧独立子入口，保留具有启用子项的来源父入口。
- `lib.rs:17414` `build_router_hub_skill_md` 生成带来源及绝对子文件路径的父路由；同名且字节相同的副本去重，不同内容保留路径变体。
- `lib.rs:17793` `sync_skill_conflict_dispatchers_for_skills` 清理旧受管全局 dispatcher；历史冲突选择只是兼容记录，不能据它判断当前全局排他行为。

本机 `.agents/skills/paperspine`、`.codex/skills/paperspine`、`.claude/skills/paperspine` 最终指向受管父路由；重复来源也生成了自己的父入口。这是重复身份问题，不是别的来源抢占了 paper-spine 这个名字。

找到的边界缺口是真实代码缺陷：旧 `delivery_manifest_is_valid` 接受任何 `sources_root` 内的子文件，手动修改父路由后可把另一个来源的子文件作为自己的子项；目录采集仅依靠普通 symlink 判断，Windows junction 还可越界遍历。

本轮局部修复：

1. 从父路由的 Managed source/管理来源字段定位唯一受管来源；校验单段路径和父入口名字关系，旧无该字段的路由只回退到同名来源。
2. canonical 后的来源必须是 sources 的直接子目录，不能是链接。
3. 每一个子文件必须实际位于该来源下，且不是链接文件。
4. 收集来源子 Skill 时，使用 `external_skills::is_link` 排除符号链接及 Windows reparse/junction，逐目录检查 canonical 边界。

新增测试覆盖：同名子 Skill 在另一个来源中时不能通过父路由验证；来源内 junction 指向另一个来源时不采集外部子 Skill。测试位于 `source_identity.rs`，调用真实路由 helper，未复制实现做假测试。最终 cargo 运行由主代理统一进行。

## 4. 自动同步会不会覆盖手写备注

没有证据表明正常重新分析会覆盖已有非空手写备注。`lib.rs:1319` 的 `reanalyze_library_metadata_blocking` 重新扫描后通过 override-aware 的索引读取返回，并记录 `manualOverridesPreserved`；`lib.rs:7827` 的 `persist_snapshot` 刷新基础来源/Skill 表，但保留 overrides 和用户标签记录。

PaperSpine 就是本机反证：基础 `sources.note` 已变成多语言导航和“3 个子 Skill”，手写 `source_overrides.note` 仍保留较早的用户说明和“1 个子 Skill”。这会让文本显得过时，但不能作为用户备注被智能分析重写的证据。

旧 `read_indexed_sources` 用 `COALESCE(NULLIF(override.note,''), sources.note)`，会让明确清空备注重新显示自动内容。本轮 `lib.rs:8338` 改为在存在手动 display_name/source_type/category_id/note 时尊重手动 note，包括空文本；单独评分或启停不算手动编辑元数据。独立合并模块的 `read_source` 已对齐这一读取语义。

仍需保留的边界：如果未来允许单独只编辑/清空备注且不保存其他手动元数据字段，应用应新增明确的 note ownership 标记，不能永远靠其他字段推断。当前元数据编辑入口统一保存字段，主代理应以回归测试证明该路径。

自动摘要另有质量问题：`metadata.rs:162` `analyze_source` 可能选择 README 导航行；目录的物理子项计数与去重后的能力数也不总相同。应修改推断层和 UI 标注，不修改用户已有备注。

## 7. 节省 token 的后续实施顺序与验收

先完成本轮来源身份和状态保护再扩客户端数量。为每个小任务给固定文件范围、输入输出和失败条件，避免让多个模型重复阅读全文或同时编辑巨型 lib.rs。

1. **本轮收口：来源身份幂等。** 旧 basename 已存在时再导入同 URL 不新增目录或 source id；SSH/大小写形式归一；不同 owner 同名仓库仍可并存；有内容差异/子项设置的重复源不得自动消失；模拟中途失败必须留下可恢复状态。
2. **持续项目列表和实例详情。** 独立模块记录项目根和最近扫描，不做全盘扫描；同名不同内容和同内容不同位置均可查看；移除项目登记不删磁盘文件；已知目录中的链接越界被明确跳过。
3. **客户端能力表。** 每行分开“检测到软件/发现 Skills/支持投递/支持 MCP”；先把现有三个受支持目标验证完整，再按一个客户端一个适配器扩展；测试使用临时 home，不在测试中创建真实客户端目录。
4. **更新与冲突预览。** 只有建立原始内容 baseline 后才做双向更新；结果分未变、可更新、本地修改、双方修改、权限失败；所有写入逐项备份，不用 mtime 自动判胜。
5. **内容品质与依赖。** 改摘要导航过滤、能力数与实例数，详情显示引用文件/依赖；市场内容导入前展示来源和许可。此阶段不阻塞已发现和可安全管理的基本能力。

本轮独立模块 API：`canonical_github_identity(&str) -> Option<String>`；`merge_source_metadata(&mut Connection, primary_id, duplicate_id) -> Result<SourceMergeReport,String>`。后者需要无外层事务，内部使用 IMMEDIATE 事务，只合并元数据，不删除来源行或目录。主备注、评分、分类优先；额外分类和过长副备注记录在 report；子 Skill 设置不做猜测映射，保留/阻止物理合并并依靠完整备份。若未来实现子项迁移，应先按真实 `skills.relative_path` 剥离 `github_sources/<source-folder>/` 后匹配，父路由单独处理；不能按 folder_name，因为其可能已带来源前缀。

当前独立测试包括 URL 规范化及拒绝伪域名、主值优先和重复合并幂等、事务中途失败回滚、缺失分类继承/过长备注保留、跨来源父路由拒绝、Windows junction 跳过。主代理统一运行最终 cargo/UI 检查；未取得最终日志前，本报告不填写通过数量。

## 最终核验更正

同一 HEAD 不等于完全相同的工作树：新 PaperSpine 是 sparse-checkout。主代理逐文件检查确认新副本为旧完整副本的严格子集，无独有或不同文件；最终按内容包含关系保留完整副本。完整测试和本机执行记录见 v3.2.6-implementation-and-validation.md。
