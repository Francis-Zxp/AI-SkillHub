# v3.2.5 参考项目审查、已修缺陷与后续交接

日期：2026-09-20。范围：用户指定的五个仓库、本仓库真实 Tauri/Rust/React 实现、来源快照更新与删除路径。第三方仓库只读取代码、许可证和元数据，未执行其安装脚本或程序。本报告不代表 Windows 10 实机验收，也不声称已经审完每一行代码。

## 1. 结论

用户指出的关键差距成立：AI SkillHub 原有 `scan_legacy_snapshot_under_write_guard` 从配置的中央 skills 与 sources 目录建立技能索引，Agent 配置更多用于检测和分发；这不等于枚举每个工具实际能看到的全部技能。一个已经由 npx、插件或手工安装的 Skill，可能在工具中有效，却不在中央技能库。

最值得学习的是“真实位置作为事实、中央库作为管理选择”的设计。先把全局与项目中的技能看全，再给出明确的导入、链接、复制与冲突处理。继续扩充首页动画或单纯增加支持工具数量，不能解决这个差距。

本仓库已经有 Tauri 2、React、Rust、SQLite、隔离导入、安全扫描、来源分发、MCP 配置事务和签名更新；旧 `FEATURE_MATRIX.md` / `TECHNICAL_ROADMAP.md` 部分表格仍称 v1/原型，不能据此重做整个架构。当前升级应复用已有实际能力。

## 3. 功能与实现迁移判断

### A. 外部技能发现：第一优先

xingkongliang 的 `scan_local_skills_with_adapters` 扫描每个已检测工具的主目录和 additional_scan_dirs。`collect_skill_dirs_recursive` 用 canonical path 集合避免链接循环；发现记录保存 tool、found_path、fingerprint；`group_discovered` 以名字与内容指纹聚合，避免把同名异内容技能误合并。这是我们最需要的逻辑，不能只从数据库中已有 Skill 反向查询 Agent。

本项目应保留“路径实例”和“内容身份”两个层次：一个文件夹同时被多个 Agent 看到，要显示多个位置，而不是产生几个误导性的独立安装。外部内容只能在用户选择导入后复制入管理源；扫描阶段不重命名、不补文件、不删除外部目录、不凭空创建未安装工具的目录。

与当前父子路由兼容：不要把来源根的路由入口和真实子 Skill 简单按同名折叠。插件缓存应单独标注宿主管理归属，优先只读，避免编辑后被宿主更新覆盖。

### B. 项目工作区：第二优先

xingkongliang 的 `ProjectSkillInfo` 同时记录 agent、relative_path、enabled、in_center、sync_status 和内容 hash；项目扫描只看配置的 Agent 相对 skills 路径。jiweiyeah 的 `SkillScope`、project binding 与 instance_id 说明，同名全局技能与项目技能必须能同时存在。

沿用本仓库已注册 workspace，不默认遍历整块磁盘。建议页面先选择工作区，再选择全局/项目；每项显示真实路径、来源及可用动作。先完成项目发现、详情和复制入库，再做双向更新。双向同步需要可信 baseline 与冲突预览，不能直接套用“最新修改时间获胜”。

### C. 分发矩阵、组合包与导入预览

技能详情显示一排 Agent 状态，状态来自实测路径而非数据库布尔值。动作分为“加入这个工具”“从这个工具移除”“从中央库删除”，避免一个删除按钮含义不明。组合包优先表达一次性分发清单；持续同步是独立选择。

jiweiyeah 的 transfer 模型把结果分为 imported、skipped、overwritten、renamed、failed，并先 preview；这种反馈值得迁移。但该版本 `ConflictStrategy::Overwrite` 在解包前 `remove_dir_all(target_path)`，与我们的备份要求冲突，不能照抄操作顺序。我们的实现应在隔离目录完成校验，备份旧目录，再原子切换，失败恢复。

### D. 市场与 MCP：保留类型区别

市场入口可以学习分类、搜索与作者/许可/版本展示。Tons of Skills 把 canonical、generated adapter、package、upstream mirror 分开，来源锁记录具体 commit 和每文件 hash，比仅显示“GitHub 来源”更有价值。

本次没有证据证明上述三个桌面管理器提供了比本仓库更完整的 MCP 事务管理；不要把它们的 Skill 市场功能写成 MCP 管理功能。AI SkillHub 已有 `mcp_center.rs`、`mcp_github_import.rs`、`mcp_mutation.rs`；继续沿用“不启动服务器、先计划后应用、未知字段保留、秘密不回传、可回滚”的实现。市场插件中包含 MCP 时，应解析到 MCP 导入预览，而不是当作一个 SKILL.md 文件夹安装。

## 4. 本轮代码发现与修复

行号会随并行编辑变化，以函数名为稳定锚点。

### P1：相同文件长度的更新永远被判为无变化（已实现修复）

位置：`app-next/src-tauri/src/lib.rs` 的 `snapshot_tree_fingerprint` 与 `refresh_single_snapshot_source`。

原实现只 hash `(相对路径, 文件长度)`。例如 `# One` 改成 `# Two`，文件内容变了而长度相同，刷新直接返回 unchanged。原回归测试把 `# One` 改成更长文本，只证明“长度变化”有效，没有覆盖内容变化。

改动：按文件流式 SHA-256，排序后把相对路径和文件 hash 汇总；排除仅用于记录下载时间的管理元数据。目录读错误不再悄悄忽略；遇到链接保留本地副本并停止自动替换。测试改为同长度文本变更。

### P1：ZIP 回退来源更新可能覆盖用户本地修改（已实现修复）

位置：同文件 `write_managed_source_metadata`、`snapshot_refresh_preflight`、`refresh_single_snapshot_source`；日志映射位于 `app-next/runtime/SkillHub.ps1` 的快照结果 switch。

原实现只对真正 Git clone 检查 dirty；ZIP 来源无 `.git`，只要上游与本地不同就整树备份并替换。最多保留三份备份不是防止覆盖本地修改。

改动：新下载记录 `baselineSha256`；上游变化时先检查本地是否仍等于下载基准。本地编辑、增加或删除文件都保护性跳过。旧版本没有基准的副本，仅当本地与新下载内容完全相同时自动补基准；存在差异则保留本地并明确提示先备份、复核、再重新导入。相同内容核验也更新时间，避免一直占据“最旧快照”队首。`local-changes` 显示为 skipped，不谎报更新成功。

回归函数 `snapshot_refresh_protects_local_changes_and_migrates_matching_legacy_copies` 覆盖干净副本更新、同长度本地修改、本地新增/删除、旧副本冲突保留、旧副本安全迁移及迁移后的正常更新。主任务反馈统一 Rust 测试中的 snapshot 测试已通过；最终完整测试统计以主任务记录为准。随后链接判定复用 `external_skills::is_link`，覆盖 Windows reparse point/junction，需纳入最终测试。

已知边界：管理 marker 的 JSON 写入沿用 `fs::write`，不是原子替换。当前唯一完整原子写 helper 在 MCP 私有事务模块中，耦合配置权限、指纹与 journal，不直接跨模块借用。若在 marker 写入时断电，可能留下损坏 marker；下次刷新会解析失败并保留全部 Skill 文件，自动更新需修复 marker/重新导入。后续可抽取独立原子 JSON writer，但不为这次修复改动 MCP 事务。

### P1 待修：来源删除不是完整事务

位置：`delete_managed_source`（检查时约 3692 行）。顺序是移动源文件夹至备份、修改 runtime config、删除 SQLite 状态、删除治理状态、写审计、重新分发。后续任一步返回 Err 都没有反向恢复之前成功的文件/配置步骤。文件有备份，因此不是立刻不可恢复删除；但用户可能收到“失败”，实际来源已经移走且链接损坏。

建议故障注入：在配置写失败、数据库锁定、分发失败三个阶段分别触发错误；要求原目录/配置/数据库/Agent 链接回到一致状态，或留下可恢复 journal 并在下次启动修复。未做此故障注入前，不应称整个删除链路已经可靠。

### P2 待验证：跨盘移动失败后的部分目标目录

位置：`move_directory`。rename 失败后改用 copy 后删除；copy 中途失败可能留下部分目标目录。`refresh_single_snapshot_source` 的恢复再次向目标复制时，需要证明不会把新旧树混合。建议跨盘/注入 copy 失败的夹具，目标只在 staging 完成后晋升；不能因这个发现随意删除用户来源目录。

## 5. 最省 token 的分阶段执行包

每个阶段只给执行模型：本节任务、允许改的文件、输入/输出契约、失败场景与验收命令。不要让每个模型重新读五个完整仓库或重写所有页面。一个模型负责方案和最终 review，功能模型负责互不重叠模块；同一份 lib.rs 只由一个整合者集中注册命令。

## 6. 发布与证据要求

v3.2.5 的验收应分别列清楚：源码修复、自动测试、本机 UI、朋友 Windows 10 实机、签名安装包及更新渠道。构建成功不能替代朋友电脑上的显示验收；把版本号改成 3.2.5 也不等于已经正式发布。远程来源读取失败、无权限扫描、保护性跳过都应保留具体状态，不能统一显示“成功”。
