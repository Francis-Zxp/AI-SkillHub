# AI SkillHub MCP、Codex 诊断与 macOS 产品扩展方案

日期：2026-08-07  
基线：AI SkillHub v3.0.7 公开正式版  
状态：P0 只读基础已在 `codex/v3.1-readonly-foundation` 分支实现；安全写入、运行诊断与 macOS 仍是后续阶段

## 1. 结论

1. 保留 `AI SkillHub` 主品牌，暂不改名。对外副标题改为“AI 能力与连接管理中心 / AI Capability & Connection Hub”。现有 GitHub、抖音和用户认知比一次宽泛改名更有价值。
2. MCP 值得加入，但必须是独立的“连接中心”，不能混入 Skill 列表。Skill 是给模型阅读的操作手册；MCP 是让 AI 主机在运行时访问工具、实时数据和外部动作的标准协议。
3. 桌面的“Codex 插件健康检查”适合并入“诊断中心 → Codex 内置插件医生”，不适合继续作为独立产品，也不能宣传成通用 ChatGPT 插件修复器。
4. WorkBuddy 适合作为外部 MCP/工作流运行时进行检测、接入和诊断，不适合作为 AI SkillHub 的普通 Skill 目标，也不复制或打包其 GPL-3.0 代码。
5. macOS 版可以开发，但当前 Windows 核心逻辑不能直接复用。必须先把 PowerShell、junction、AppX/注册表和 Windows 路径拆成平台适配层，再做 Apple Silicon/Intel CI、签名公证和真实 Mac Beta。
6. 下一阶段采用两条并行产品线：`v3.1 MCP 只读发现与诊断`，以及 `macOS 平台解耦基础`。在只读盘点和数据迁移门禁通过前，不开放跨客户端自动写配置。

## 2. 用户心智模型

| 概念 | 一句话解释 | AI SkillHub 中的位置 |
|---|---|---|
| Skill | AI 阅读的操作手册、方法和工作流说明 | 能力库 |
| Prompt | 可复用的任务指令或材料模板 | 能力库 |
| MCP Server | 向 AI 提供工具、资源和实时数据的运行时服务 | 连接中心 |
| AI 工具/Host | 使用 Skill 和 MCP 的客户端，如 Codex、Claude Code | AI 工具 |
| Adapter | AI SkillHub 用来识别并安全读写某个 Host 的适配规则 | 后台能力，在 AI 工具与诊断中心呈现 |
| Plugin | 厂商定义的扩展包，可能同时包含 Skill、MCP 和 UI | 诊断/生态详情，不与 MCP 画等号 |

MCP 可以类比“AI 应用的 USB-C”。它不只是连接另一个软件的快捷方式，而是规定了主机、客户端和服务端如何发现能力、交换上下文、请求工具调用并获得结果。MCP 服务端可能是本机命令，也可能是需要 OAuth 的远程服务。

## 3. 为什么现在加入 MCP

- 用户需求已经明确出现，且 Codex、Claude 等主流工具均支持 MCP。
- AI SkillHub 已经有来源、适配器医生、快照、审计和回滚，具备比从零制作 MCP 配置编辑器更好的安全基础。
- MCP 能把产品从“Skill 文件管理器”升级为“能力与连接控制面”，与真实关系图谱、父子路由和个人评分形成互补。
- 只做一个 JSON/TOML 表单价值不大；真正差异化应是跨 Host 归一化、变更预览、凭据引用、健康诊断、快照和回滚。

### 不采用的两个极端

- 不只做“复制 MCP 配置”的快捷按钮：它无法处理作用域、冲突、凭据、客户端差异和回滚。
- 暂不自建公共 Registry、云同步或统一 MCP 网关：这会同时引入服务端运营、供应链信任、运行时隔离和团队权限，范围过大。

## 4. MCP 连接中心信息架构

主导航建议收敛为：

1. 仪表盘
2. 能力库（Skills、Prompts）
3. 连接中心（MCP）
4. AI 工具
5. 诊断中心
6. 设置

普通模式只显示 MCP 服务卡片：名称、Local/Remote、风险级别、已配置到哪些 AI 工具、作用域和发现状态。P0 不启动未知服务，所以必须显示“能力未探测”，不能从静态配置伪造 Tools/Resources/Prompts。高级详情再显示脱敏命令/URL、环境变量引用、来源和按需配置比较，避免重新制造过长的“分发矩阵”。

### 核心页面

- 总览：已配置服务、有效绑定、需要处理、凭据引用缺失。
- 服务详情：来源、配置实例、Host、作用域、优先级和脱敏安全发现；真实能力与健康历史只在后续显式运行诊断后显示。
- 添加连接：官方 Registry 搜索、粘贴配置、从客户端导入、本地命令、远程 URL。
- 变更计划：写入前展示目标文件、字段级差异、备份、风险和回滚入口。
- 凭据：P0/P1 首期只保存环境变量/Header 名称和 present/missing/inline-secret 状态；OAuth 调用 Host 原生登录，不截获 token。只有确有跨 Host 统一凭据需求时才评估自有 vault。

### 数据模型

- `mcp_scan_runs`：一次只读扫描及统计。
- `mcp_config_locations`：Host adapter、原生作用域、相对位置、hash、解析状态和优先级；Host 配置仍是真实事实源。
- `mcp_servers`：由 transport/目标/来源 fingerprint 归并的逻辑 Server。同名不等于同服务。
- `mcp_bindings`：某个 Host/作用域配置中的一次实例，记录 native name、enabled/effective/approval/auth 与片段 hash。
- `mcp_secret_requirements`：只保存变量/Header 名称及 present/missing/inline-secret，不保存值。
- `mcp_findings`：损坏、重复、漂移、路径失效和疑似明文凭据的脱敏证据。
- P1 再增加 `mcp_profiles`、变更计划、步骤 journal 与受平台保护的备份；`mcp_health_runs` 和 capability observations 延到显式运行诊断。

## 5. MCP 安全边界

本地 stdio MCP 与安装本地软件的风险接近，会以客户端权限启动进程。因此默认流程必须是：

`只读发现 → 能力/命令/权限证据 → 变更 diff → 用户确认 → 快照 → 原子写入 → 验证 → 可回滚`

硬规则：

- 发现阶段不自动执行未知 MCP 命令。
- 健康检查必须有超时、输出上限、取消和最小权限；条件允许时使用沙箱。
- 不把 token 写入 SQLite、日志、诊断包或前端状态；首版只管理引用名称，OAuth 交给 Host 原生登录。
- 配置文件可能已经含有 inline secret。精确备份会复制秘密，因此没有 DPAPI/Keychain 保护、用户专属权限和过期策略时必须保持只读，不能生成第二份明文。
- 项目级 MCP 配置必须显示仓库来源和待执行命令，并尊重 Host 自身的信任确认。
- 首版支持稳定的 `stdio` 与 `Streamable HTTP`；旧 SSE 只做兼容导入，不成为新建默认。
- 官方 Registry 用于发现元数据，不代表 AI SkillHub 为第三方服务安全背书。
- 深度协议调试优先复用/启动官方 MCP Inspector，不自行重造完整 Inspector。

## 6. 分阶段交付

### v3.1：MCP 只读发现与诊断

- 第一批只读取 Codex family 与 Claude Code 的 MCP 配置；Claude Desktop 等到独立 Windows/macOS 夹具后再加入。
- 标准化 stdio/HTTP、作用域、环境变量引用和能力摘要。
- 静态配置只显示“能力未探测”；不运行任何 Server、CLI、npm 或 OAuth。
- 显示重复定义、路径失效、缺少命令、未知字段和配置漂移。
- 不写配置、不启动未知服务、不保存密钥。
- 完成 Windows 收件人回归和临时 HOME 配置夹具测试。

验收：扫描前后每个配置的 SHA-256/mtime 不变；同名不同目标不误合并，同一服务多作用域能正确显示优先级；SQLite、IPC、日志、控制台和诊断包不含凭据值；损坏 TOML/JSON 只生成 finding，页面不崩；500 bindings 分页仍响应，扫描可取消。

### v3.2：安全绑定与配置治理

- 从官方 Registry/配置片段添加服务。
- 绑定到选定 Host 和作用域；提供 Profiles。
- 字段级 diff、快照、原子写入、写后解析验证和一键回滚。
- 只管理凭据引用和缺失状态；OAuth 打开 Host 原生登录。配置备份必须平台加密、限制权限/保留期且永不进入诊断包，否则该文件保持只读。
- 客户端适配器必须各自通过读写往返测试。

### v3.3：运行诊断与团队清单

- 用户显式授权后才执行有界健康检查并记录 observed-at/protocol version；日志摘要和版本/来源治理不能把运行时观察冒充静态真相。
- 官方 MCP Inspector 入口。
- 可导入导出的声明式清单；清单不包含密钥。
- 真实工具调用 benchmark 只作为显式 opt-in 实验，不冒充静态健康评分。

## 7. Codex 内置插件医生整合

当前桌面快捷方式实际以 `-ExecutionPolicy Bypass -AutoRepair` 运行 `~/.codex/plugin-health/CodexPluginHealth.ps1`，只针对 Windows Codex AppX 内置的 Chrome 与 Computer Use bundled 插件。它检查 AppX 版本、资源路径、UTF-8 BOM、插件缓存、Computer Use runtime、Chrome native host/注册表和 `codex plugin list`。

独立审计确认它不能原样并入产品：所谓扫描会从本地 Skill/受管理来源按时间戳同步 repair engine，没有发布签名或固定哈希；还会执行插件缓存中的 JS、Computer Use `setup.ps1` 和 PowerShell 修复脚本。即使去掉 `AutoRepair`，当前扫描也不是严格只读。内置版必须重写为 Rust 只读探针，修复规则只能来自通过 AI SkillHub 更新签名验证的程序版本。

推荐放置：`诊断中心 → AI 工具医生 → Codex 内置插件`。

交互：

1. 默认只读扫描。
2. 每条问题显示证据、影响和建议操作。
3. 用户选择要修复的项目。
4. 备份相关配置和允许范围内的缓存。
5. 执行固定版本规则。
6. 重扫验证；失败可回滚。

边界：

- 不默认 `-AutoRepair`，不静默修改环境变量或注册表。
- 不从 Skill、来源仓库或插件缓存同步并执行修复引擎；不无条件执行 PS1/JS/setup 脚本。
- 只读探针直接读取 AppX 元数据、JSON/TOML、SHA-256、环境变量和精确白名单注册表键，扫描前后文件树/注册表/环境变量必须不变。
- 未识别的新 Codex 版本只诊断不修复，直到兼容规则验证。
- 仅允许精确的 Codex 插件路径、官方包和注册表键。
- 报告隐藏用户名、绝对路径中的个人段和环境变量值。
- macOS 不显示 Windows 修复卡；未来建立独立 macOS Codex 诊断规则。
- 迁移完成前保留独立工具作为回滚手段，确认内置版稳定后再提示用户卸载快捷方式。

## 8. WorkBuddy 定位

WorkBuddy 是围绕 Claude Code 与 Obsidian 的本地优先个人 Agent 运行时。它用 MCP 网关暴露搜索、执行、推进和状态能力，并提供持续任务、DAG 工作流、记忆、审批和 Dashboard。它更像“本地个人工作操作系统”，不是另一个普通聊天窗口。

推荐集成方式：

- 检测 WorkBuddy CLI/sidecar/MCP gateway 是否存在。
- 将其 MCP gateway 作为连接中心的一项外部服务导入。
- 在适配器医生中检查端口、配置、状态和版本。
- 提供打开其本地 Dashboard 的明确入口。
- 不读取其私有记忆内容，不代替它管理工作流。
- 不复制或打包 GPL-3.0-only 源码；通过公开配置/协议互操作。

WorkBuddy 目前仍是 Beta，README 表明当前以 Windows 安装为主、macOS/Linux 仍在推进，因此首版标记为“实验性生态集成”，优先级低于通用 MCP 控制面。

## 9. macOS 产品与工程计划

当前阻塞不是 Tauri 窗口，而是核心行为仍依赖 PowerShell、Windows junction、AppX/注册表、Windows 用户目录和仅 NSIS 的发布配置。

### M0：平台抽象

- 将同步、来源导入、SQLite 迁移和主要诊断从 PowerShell 迁入 Rust service。
- 建立 `PlatformAdapter`：路径、应用检测、进程、凭据库、文件链接、更新器。
- 建立 `LinkStrategy`：Windows junction；macOS 使用经验证的 symlink 或可回滚 managed copy。
- 每个 AI Host 使用独立 config/path locator；不凭猜测创建目录。
- 不支持的能力显示“当前平台暂不支持”，不创建假目录或假成功。

### M1：双架构 CI

- GitHub Actions 同时构建 Apple Silicon 与 Intel macOS。
- 在临时 HOME 下测试 SQLite 新装/升级、来源导入、路径检测、链接、MCP 配置读写往返和更新清单。
- 生成 `.app`/`.dmg` 预发布资产；失败时不得覆盖 Windows latest 稳定通道。

### M2：签名、公证与更新

- 增加高分辨率 `.icns`。
- 使用 Apple Developer ID、Hardened Runtime、notarization 和 stapling。
- 更新清单分别提供 macOS Apple Silicon、Intel 与 Windows 签名资产。
- 用户资料目录与安装目录分离，升级/卸载不删除来源、评分、标签、备注和数据库。

### M3：真实 Mac Beta

- 招募 2–3 位现有粉丝：至少 Apple Silicon，条件允许再覆盖 Intel。
- 提供单独 Beta 通道，不直接成为 stable latest。
- 验证安装、Gatekeeper、首次权限、导入、Claude/Codex 检测、MCP 配置、升级保留、卸载残留和回滚。
- 只收集用户主动导出的脱敏诊断，不静默遥测。

Windows 电脑与 GitHub macOS runner 可以验证构建和自动化流程，但不能替代真实 Mac 上的 Gatekeeper、权限、窗口手感和第三方 AI 工具集成测试。因此通过真实 Beta 前，不宣称“macOS 正式版完全验证”。

## 10. 品牌与版本建议

暂不改名：

- `AI SkillHub` 已经在 GitHub 和抖音形成初步认知。
- Skill 仍是产品最有辨识度的入口，MCP 是扩展而不是推翻。
- 频繁改名会削弱搜索、教程、更新通道和用户信任。

建议表达：

- 中文：`AI SkillHub｜AI 能力与连接管理中心`
- 英文：`AI SkillHub — Capability & Connection Hub`
- 首页短文案：`管理 Skills、MCP 与 AI 工具连接。可发现、可解释、可回滚。`

等 macOS、MCP 安全写入和至少 6 个高质量 Host 适配器稳定后，再评估 v4 是否需要更宽的品牌名。

## 11. 优先级与范围

| 优先级 | 工作 | 原因 |
|---|---|---|
| P0 | GitHub 导入可靠性、平台抽象、MCP 只读发现、Codex 医生只读整合 | 先修收件人阻断问题，再共享跨平台/诊断基础能力 |
| P1 | MCP 安全写入/回滚、macOS CI/签名/Beta | 用户明确需求，也是正式跨平台门槛 |
| P2 | WorkBuddy 适配、团队清单、Profiles | 建立在通用 MCP 模型之上，避免一次性专用代码 |
| P3 | 云同步、公共社区 Registry、自有 Gateway | 运营和安全成本高，需等本地控制面成熟 |

## 12. 成功指标

- 只读扫描 0 文件变更、0 密钥泄露、0 未授权进程启动，损坏配置不崩溃。
- 任一 MCP 写入都能展示 diff、生成快照、写后验证并回滚。
- Windows → 新版升级保留现有 38 来源/650 Skill 基线及所有本地元数据。
- macOS 新装、升级、卸载和 Apple Silicon/Intel CI 全通过；真实 Beta 无阻断级问题。
- Codex 医生未知版本不会自动修复；已知问题修复后能复测并回滚。
- 1000+ 节点图谱仍保持帧率预算，业务页面完成拆包与可访问性检查。

## 14. 2026-08-07 P0 实现检查点

已完成：

- GitHub 导入不再因仓库内合法符号链接而整包失败；链接条目只跳过并告警，绝不创建或跟随。
- 匿名 GitHub API 不再进入逐文件 Blob 下载；令牌可用时才保留 API 路径，403/429 会显示限额重置时间和处理建议。
- 导入阶段由 Rust 发送真实事件：检查、系统 Git、ZIP 下载、归档检查、安全扫描、写入；未知总量使用不确定进度动画，并可取消和清理隔离暂存目录。
- “连接中心”已加入主导航。首版只读盘点 Codex 与 Claude Code 配置，将 Host、逻辑 Server 和 Binding 分离；不启动 MCP、不探测能力、不保存凭据值。
- “Codex 插件医生”只读卡已加入 AI 工具页。Rust 探针只检查安装、配置、缓存与清单证据；`repair_available=false`、`write_capable=false`、`mutation_count=0`。
- 桌面的独立 `Codex 插件健康检查` 未运行、未修改、未复制；在内置医生具备签名规则、备份、确认、复测和回滚前继续保留。

2026-08-08 已进入 `v3.1.0` 正式版候选：本机真实 Imbad codeload、符号链接跳过、逐文件扫描与运行中快速取消均已通过；只有签名安装/升级、隔离收件人桌面验收和干净 `windows-latest` CI 全部通过后才会发布。macOS 构建、MCP 写入/启动/OAuth 与插件修复仍属于后续阶段，不因本次升版提前开放。
